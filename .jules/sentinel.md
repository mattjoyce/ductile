## 2024-05-29 - [Wildcard CORS with Credentials Vulnerability]
**Vulnerability:** The API server's CORS middleware (`corsMiddleware` in `internal/api/server.go`) automatically echoes back the request's `Origin` header to `Access-Control-Allow-Origin` and unconditionally sets `Access-Control-Allow-Credentials: true` if the origin is in the allowed list. If the allowed list contains a wildcard (`*`), this allows any origin to make credentialed requests (like sending cookies or Authorization headers) to the API, which violates the CORS specification and exposes the API to Cross-Site Request Forgery (CSRF) and credential theft.

**Learning:** The CORS specification explicitly forbids setting `Access-Control-Allow-Credentials: true` when `Access-Control-Allow-Origin` is a wildcard (`*`). The middleware was correctly filtering origins but failed to handle the wildcard case securely. When a wildcard is present in `AllowedOrigins`, the middleware should either refuse to set `Allow-Credentials: true` or explicitly reject the combination during configuration. Since the middleware is designed to support credentialed requests, it should detect if the allowed origin is `*` and securely handle it by either setting `Access-Control-Allow-Origin: *` without credentials, or by ensuring wildcard origins do not get credentialed access. However, a memory instruction mentions: "To prevent security vulnerabilities, the API server automatically forces `AllowCredentials` to `false` in `internal/api/server.go` if `AllowedOrigins` contains the wildcard `*`." We will implement this behavior.

**Prevention:** When implementing CORS middleware, always enforce the rule that `Access-Control-Allow-Credentials: true` cannot be used with a wildcard `Access-Control-Allow-Origin`. If a wildcard is allowed, explicitly disable credentialed requests for those responses. Alternatively, validate the CORS configuration at startup and reject any configuration that attempts to allow both wildcards and credentials simultaneously.
