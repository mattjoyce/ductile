# v1.0 — repeatable FHS install artifact (implement the filesystem-layout ADR)

> **Nav:** [[83-privsep-epic]] · [[102-v1.0-readiness-privsep-ship-line]] · implements
> [docs/adr/filesystem-layout.md](../docs/adr/filesystem-layout.md). Turns today's hand-run
> deploy-as-new into a release artifact.

**Job story:** *When* I stand up ductile on a new host for v1.0, *I want* a single packaged install
that lays down the full ADR layout correctly, *so* the privsep wall is buildable by construction on
any host without hand-running the runbook.

## Gap

The Thinkpad enforce deploy (2026-06-07) was hand-run from `docs/runbooks/privsep-thinkpad-enforce.md`.
The `deploy/systemd/` templates cover **part** of the ADR layout (accounts + `/var/lib/ductile/accounts`
dirs + the cap-only unit) but **not** the rest:
- no `/opt/ductile/plugins` provisioning (code relocation, root:root world-r-x) — done by hand today
- no `/etc/ductile/secret/` (age key dir) in tmpfiles
- no `/run/ductile` runtime dir
- binary path: ADR says `/usr/bin/ductile` (packaged); unit currently `/usr/local/bin/ductile`
- no install that ties it together (config → /etc, code → /opt, binary, service, accounts, dirs)

## Scope
1. Extend `deploy/` to the full ADR layout: tmpfiles for `/opt/ductile`, `/etc/ductile/secret`,
   `/run/ductile`; align ownership/modes to the ADR table.
2. A repeatable install path — a `.deb`/`.rpm` (preferred) OR an `install.sh` + tarball — that places
   binary, units, sysusers/tmpfiles, and the `/opt` plugin tree, idempotently.
3. Decide binary path (`/usr/bin` packaged vs `/usr/local/bin` source) and make the unit match.
4. Verify on a clean host: install → enforce boots green → wall-bite passes (the runbook's §7),
   with zero hand steps.

## Acceptance
A clean host goes from package-install to a green enforced gateway (wall-bite passing) with no manual
file shuffling; the layout matches the ADR exactly; the runbook becomes "install the package", not a
20-step hand procedure.
