# Card 148 slice 3: BLAKE3 to SHA-256, hard cut, one `config lock` migrates

The design is decided and approved on `kanban/148-shed-four-dependencies.md`
("Slice 3 design note"). Do not redesign. Read that note first.

## Change

### A. Hash primitives (`internal/config/hash.go`)

1. `ComputeBlake3Hash` becomes `ComputeFileHash(filePath string) (string, error)`: `sha256.Sum256`
   over the file bytes, returned as `"sha256:" + hex`. Doc comment:
   `// ComputeFileHash returns the SHA-256 of a file as "sha256:<hex>".`
2. `ComputeKeyedBlake3Hash` becomes `ComputeKeyedFileHash(filePath string, key []byte) (string, error)`:
   `hmac.New(sha256.New, key)` over the file bytes, returned as `"sha256:" + hex`. Keep the
   32-byte key length check and its error text, and keep the existing doc paragraph about
   unforgeability, with "keyed BLAKE3" replaced by "HMAC-SHA256".
3. `VerifyFileHash` calls `ComputeFileHash`. Update the doc comment ("expected SHA-256 hash").
4. Every caller is renamed. No identifier, comment or error string in non-test Go code may still
   say BLAKE3 or Blake3, except the legacy error in B2.

### B. Manifest version 3 (`internal/config/hash.go`, `types.go`, `plugin_lock.go`)

1. Every place that writes `Version: 2` writes `Version: 3` (`hash.go:85`, `hash.go:191`,
   `plugin_lock.go:166`). Update the `ChecksumManifest` and `PluginFingerprint` doc comments
   (`types.go:623-640`) to say SHA-256 / HMAC-SHA256.
2. Add an exported sentinel in `hash.go`:
   ```go
   // ErrChecksumsLegacy marks a .checksums manifest written by an older ductile
   // (version 2, BLAKE3). It is refused; one 'ductile config lock' migrates it.
   var ErrChecksumsLegacy = errors.New("checksums were written by an older ductile (BLAKE3, version 2); run 'ductile config lock' to re-lock under SHA-256")
   ```
   `LoadChecksums`: version 2 returns `fmt.Errorf("%s: %w", checksumPath, ErrChecksumsLegacy)`;
   any other version that is not 3 keeps the existing "unsupported checksums version" error.
3. Add `LegacyPluginNames(configDir string) ([]string, error)` in `hash.go`: reads `.checksums`,
   requires version 2, returns the `plugin_fingerprints[].name` values sorted. Used only by the
   migration in C.

### C. `config lock` migration (`cmd/ductile/config.go`, around lines 795-822)

Today `config lock` calls `config.LoadChecksums(dir)` and carries recorded fingerprints forward
with `PreservePluginFingerprints`. Add one branch: when `LoadChecksums` returns an error with
`errors.Is(err, config.ErrChecksumsLegacy)`:

1. `names, err := config.LegacyPluginNames(dir)`.
2. `resolved, err := resolveConfiguredPluginFingerprints(cfg, configPath)` (as `plugin lock --all`
   does in `cmd/ductile/plugin_lock.go`), keep only plugins whose `Name` is in `names`.
3. If any remain, get the nonce with `fingerprintNonceForConfig(dir, cfg, nil)`; on error print
   `config lock: migrating plugin fingerprints needs the vault nonce: <err>` and return 1.
4. `config.ComputePluginFingerprint(rp, nonce)` for each; the result set (sorted by Name, no
   clearpass records) is what is passed to `GenerateChecksumsWithFingerprints` in place of
   `preserved`.
5. Print, always (not only verbose), one line per plugin:
   `  REHASH [plugin] <name> (BLAKE3 -> SHA-256)` and, before them, once:
   `Migrating .checksums in <dir> from BLAKE3 (version 2) to SHA-256 (version 3).`
6. `--dry-run` computes and prints but writes nothing, as today.

The non-migration path (version 3 manifest, or no manifest) is unchanged.

### D. Clearpass seal (`internal/config/plugin_clearpass.go:94`)

`clearpassMAC` uses `hmac.New(sha256.New, nonce)` with the same NUL-delimited fields, returns
`"sha256:" + hex`. Keep the nonce length check.

### E. Confirmation code (`internal/config/plugin_lock.go:77`)

`PluginFingerprintsCode` uses `sha256.New()`; the code is still the first 5 hex characters of
the digest (no tag). Update its doc comment.

### F. Snapshots (`internal/configsnapshot/snapshot.go`)

1. Secret fingerprint (`:485-488`): `sha256.Sum256` over
   `"ductile config secret fingerprint v2\x00" + purpose + "\x00" + value`, prefix
   `"secretfp_sha256:"`.
2. `sourceHash` (`:510-523`): `sha256.New()`, prefix `"sha256:"`.
3. `hashCanonical` (`:531-532`): `sha256.Sum256`, prefix `"sha256:"`.

### G. Pipeline fingerprint (`internal/router/dsl/compiler.go:789-790`, `types.go:270`)

`sha256.Sum256`, prefix `"sha256:"`; the `types.go:270` comment says `sha256:<hex>`.

### H. Module

`go mod tidy`: `github.com/zeebo/blake3` and `github.com/klauspost/cpuid/v2` leave `go.mod` and
`go.sum`. Do not hand-edit `go.sum`.

### I. Tests (beside the code, table-driven where it fits, real temp dirs, no mocks)

1. `internal/config`: `ComputeFileHash` equals `"sha256:" + hex(sha256(bytes))`;
   `ComputeKeyedFileHash` equals HMAC-SHA256 under the key, differs from the plain hash, and
   rejects a 31- and 33-byte key. Rename `keyed_hash_test.go` tests to match the new names.
2. `LoadChecksums` on a version 2 file: `errors.Is(err, ErrChecksumsLegacy)` is true. Version 3
   loads. Version 1 gets the unsupported-version error.
3. `LegacyPluginNames` returns sorted names from a version 2 file and errors on version 3.
4. A clearpass seal made then verified round-trips; a seal with one changed field fails.
5. `cmd/ductile`: a `config lock` test over a temp config dir with one enabled plugin and a
   hand-written version 2 `.checksums` (bare 64-hex values, one clearpass record) and an
   initialized test vault (follow how existing `cmd/ductile` plugin lock tests get a nonce).
   After `config lock`: `.checksums` is version 3, every value starts `sha256:`, the clearpass
   record is gone, stdout has the `REHASH [plugin] <name>` line, and a following
   `config check` passes.
6. Update existing assertions: `snapshot_test.go:59,62`, `compiler_test.go:80-81`,
   `report_test.go:101,166,173`, `plugin_fingerprint_test.go:10,68` (length is now 71 with
   the tag), and the `scopes_hash: blake3:...` test YAML strings can stay as they are (that
   field is unread).
